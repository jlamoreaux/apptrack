### D1 schema — ported, with integrity, and verified

All **51 tables / 483 columns** applied to the real D1 database from
`drizzle/d1/0000_baseline.sql`, generated by `scripts/migration/pg-to-d1-schema.mjs` off
production's live catalog.

**Constraints and indexes are included, and that mattered.** The first pass emitted tables
and columns only. It answered "does the schema survive SQLite" but was not a cutover
artifact: production carries 28 CHECK constraints, 25 non-primary unique indexes, 56 foreign
keys and 123 indexes, and SQLite supports essentially all of them. Their absence throws no
errors — it yields a database that accepts two active subscriptions for one user, a second
default resume, and a full table scan on every `WHERE user_id = ?`.

Now emitted: **27 CHECK, 23 UNIQUE, 32 FK, 98 indexes**. Two partial-unique indexes carry
invariants the app relies on:

| Index | Invariant |
|---|---|
| `idx_user_subscriptions_user_active` | one `active` subscription per user |
| `idx_user_resumes_one_default_per_user` | one default resume per user |

CHECK bodies and partial-index predicates are translated by
`scripts/migration/pg-to-sqlite-expr.mjs` (`= ANY(ARRAY[…])` → `IN (…)`, booleans → 0/1,
`EXTRACT(dow …)` → `strftime('%w', …)`). It **throws on anything it does not recognise**
rather than emitting a weakened form, and every failure is printed as a named omission, so
a constraint cannot be silently dropped. Covered by 19 tests over the real production
expressions in `__tests__/migration/pg-to-sqlite-expr.test.ts`.

Only three things are reported as not portable:

- `idx_applications_job_description` — a GIN `to_tsvector` index; needs an FTS5 virtual
  table, which is a schema of its own rather than an index.
- `idx_promo_codes_applicable_plans` — GIN over a `text[]` stored as JSON; needs a
  `json_each()` index or a query change.
- The **24** foreign keys from `public` into `auth.users`. There is no `auth.users` in D1;
  that table becomes Better Auth's own, so they are re-pointed at the auth stage rather
  than guessed at here. (A further 24 FKs into `auth.users` are Supabase's own
  internal `auth`-schema keys and are not ours to port.)

Foreign keys are declared **inside** each `CREATE TABLE`, since SQLite has no
`ALTER TABLE ADD CONSTRAINT`. Forward references to a table created later are legal —
SQLite resolves them at DML time — and the ETL's topological insert order is what makes
enforcement survive a load.

**The money decision.** SQLite has no exact decimal and REAL would silently corrupt
currency, so all 8 `numeric(p,s)` columns become INTEGER minor units:

| Column | Scale |
|---|---|
| `comp_entries.base` / `.bonus` / `.equity` | cents (×100) |
| `comp_entries.shares` | ×10000 |
| `comp_entries.vest_years` | ×100 |
| `stock_prices.price` | ×10000 |
| `subscription_plans.price_monthly` / `_yearly` | cents (×100) |

This is a breaking change to every read and write of those columns. The ETL multiplies; the
app divides at the presentation boundary, never in the query layer — a missed conversion
misreports a salary by 100×.

Also surfaced: **SQLite cannot generate a UUID**, so every column defaulting to
`gen_random_uuid()` now requires the insert path to supply an id.

Functions, triggers, RLS policies and the materialized view are deliberately absent —
SQLite supports none of them as used here. Their replacements (trigger drain, app-layer
scoping, live aggregate, FTS5) are tracked in the migration plan.

### Data — all production rows loaded, and they satisfy every constraint

`scripts/migration/pg-to-d1-data.mjs` loaded **2,594 rows across all 51 tables with zero
failures** against the constrained schema. That is the useful result: the production data
satisfies all 27 CHECKs, all 25 unique constraints and all 32 foreign keys, so none of them
has to be relaxed for the cutover.

Row count rose from 2,323 to 2,594 between runs a month apart, which is the point of the
`--truncate` flag — this is a snapshot, and the real migration runs it once more at cutover.

`scripts/migration/verify-d1-parity.mjs` checks three things across engines: per-table row
counts, that every scaled `numeric` divided by 10^s equals the Postgres value, and that
JSON columns are parseable rather than `[object Object]`. It deliberately does not hash
rendered rows — representations legitimately differ between the engines, so that would
report noise as corruption.

### R2 — 70 of 78 objects migrated

`scripts/migration/supabase-storage-to-r2.mjs` is idempotent, so it serves both the bulk
copy and the cutover delta sync. Keys are preserved verbatim, including the doubled
`resumes/resumes/{uid}/…` prefix that stored `file_url` values depend on.

**8 objects are blocked by a wrangler bug.** `wrangler r2 object put` percent-encodes a key
containing a space while reporting the unencoded name — `put "…/resume 2.pdf"` prints
success but stores `…/resume%202.pdf`, and a later `get` of the real key misses. `put`
encodes, `get` does not, and pre-encoding is neither double-encoded nor decoded, so there is
no CLI workaround. Verified on wrangler 4.56.0.

Only legacy objects are affected: `sanitizeFilename` replaces whitespace with underscores
and is applied on upload, so nothing new can produce such a key.
